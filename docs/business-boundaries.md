# 业务范围与实现边界

更新：2026-11-03。本副本是可运行的工程资料一致性审查原型，面向膜结构项目的设计工程师、材料采购和审核人。它输出问题线索与证据，不签发工程合格结论或正式报价。

## 一个具体业务场景

设计工程师提交项目 A-120 的设计要求、PTFE-502 规格书和历史采购记录。平台先验证三份文件属于同一已授权项目、已完成解析索引，再冻结本次选定的资料范围。设计要求名义厚度 0.8 mm，规格书写 0.7 mm，双方适用版本均为 R1，于是形成一个需要人工确认的问题，而不是直接说材料不合格。审核人查看原文、核实容差及设计变更，可将问题解决或填写忽略原因；报告使用版本锁批准或退回。新资料需要重新审查，不能悄悄覆盖原报告。

金额示例、项目编号和上述材料组合均为合成业务情境。真实价格不能靠公开网络随意拼接：地区、税、日期、型号和采购口径不同，数字不具可比性。

## 四种容易混淆的版本

| 字段 | 含义 | 当前实现 |
|---|---|---|
| 上传版本 `documents.version` | 本系统资料版本和幂等身份的一部分 | 整数元数据，不参与正文数值比对 |
| 文件自身版次 | 设计 D3、供应商规格 S7 | 可以不同；只有明确同一文件编号同时出现多个有效版本才提示冲突 |
| 项目适用版本 | 本次设计/采购依据 R1 | 厚度比较按明确的适用版本分组 |
| 历史/作废状态 | 原依据是否已被替代 | 当前以正文“历史参考/已作废/已替代”等标记识别，尚非完整 PLM 生效管理 |

不能仅因为不同文件的上传版本、文件名或创建时间不同就认定业务冲突。未注明适用版本且数值不一致时，提示适用范围待确认，保留人工判断。

## 当前规则

- 设计、规格、价格分别识别资料角色。设计文档出现“膜材”不能同时证明已存在独立规格书。角色识别仍是标题/正文规则，复杂混合资料需要人工拆分或声明类型。
- 厚度按材料型号和适用版本分组，以 Decimal 将 mm、微米、m、cm 归一为毫米。缺单位、多型号、多数值不强行配对。名义值不同是复核线索，不能替代厚度定义、容差及产品合格判定。
- 相同文件编号且有多个未标作废版次，提示版本冲突。不同编号、正常历史演进和不同型号不混合比较。
- 设计材料引用必须由独立规格证据支撑；缺设计/材料依据会进入人工处理；价格仅在已选包包含价格资料时检查，不强制要求报价。
- 价格检查只在同型号、地区与税口径内比较币种；跨日期提示历史可比性。缺型号、地区、税或面积币种单位需人工补证。当前未支持汇率自动换算、运费、供应商阶梯价或采购数量效应。
- 规则不是通用事实抽取器。公开厂商 PDF 的“涂层保护区厚度”不能当“膜材总名义厚度”；复杂表格、多个参数或非支持材料命名需要人工核验，不能按字符串直接做工程结论。

## Agent 工具边界

在线流程：授权并收集证据 → Supervisor 计划 → Supervisor先并行调用 `review_retrieval/review_material`，再调用 `review_review` → 领域结构化输出 → 校验与一次覆盖补审 → 汇总规则和模型发现 → 持久化 → 人工复核。

领域工具的 schema 只接受可选关注点。用户、项目、Evidence 和记忆从服务端闭包注入，不允许模型指定别的资料范围。同请求重复调用复用该领域结果。领域工具自身无数据库写、Shell 或审批能力。

full覆盖检索、材料、审查三个角色；API模式使用Supervisor受限规划，focused可以缩小范围，选择综合审查则自动补齐前置角色。Fake/禁用规划时采用确定性策略。最终报告来自实际领域工具结果；检索仅整理证据，综合审查必须等取证完成。

领域仅看到路由后的证据子集，不能把子集中没看到其他领域资料解释为全包缺证。服务端传入当前 UTC 审查日期。模型需要明确报告 processed/skipped；未报告不自动算已处理。每个领域自己的应处理集合都须覆盖，不能由另一领域代替“已审过”。最多补审一轮，仍缺覆盖则转人工。

模型的正常说明、一般范围限制和真正阻断项分开。阻断项须给出具体检查、缺失事实、原因及定位证据；模型的冲突发现必须有可见且已声明处理的引用，问题状态和编号由服务端控制。有效引用仅证明引用存在，不证明语义蕴含成立。

单包默认最多1000个证据单元、估计100000个证据Token；领域内按上下文预算分批，单片超限显式拒绝，不能以静默截断冒充全包完成。当前跨批事实归并仍有限，批次内模型看不到另批全文；全包规则会运行，但不替代复杂跨批语义比对。报告引用包含证据文本与原文件SHA，文件自身版本不从上传元数据猜测。

## 人工闭环与任务边界

本地模式有报告级 `POST /api/v1/package-reviews/{id}/decision`。批准须先处理所有冲突/需人工的问题；忽略、退回须说明原因。问题处理和决定在事务内使用 `lock_version` 比较交换，记录 actor、action、reason、时间和旧版本；批准或退回后的报告禁止改问题。审查记录的 `usage.human_review_events` 暂存这些操作元数据，目前不是独立的合规审计系统。

`completed`只表示自动审查结束且当前无阻断项，不等于人工批准；它仍可由审核人批准或退回。`worker_results`与报告正文保留生成时发现，人工问题处理以`issues`状态和操作事件为准，不能把批准理解为改写了原文事实。

Temporal以Workflow为任务权威。真实开发Server已通过Worker强杀/恢复、报告提交后失败重试、Worker离线期间决定、取消及5份新历史重放，业务库SQLite、模型Fake、解析TXT。审批持久化后由Activity轮询消费，Signal只唤醒。解析采用执行/attempt认领与写入围栏，避免遗留indexing和旧尝试覆盖。生产集群、旧生产历史升级及Full存储故障仍未验收。

同步本地模式只用于小包演示；请求完成前不存在可供取消的持久后台任务。不能把它描述成可靠队列。Temporal 是持久长任务的唯一实现，不引入第二套任务队列。

## 检索能力应如何表述

工作台资料页已提供声明编辑、版本冲突重载、条件检索与证据抽屉。声明不等于专家确认；119文档/30查询的合成开发回归仅验证本地词项和条件，3条语义改写全部漏召回，不能称语义检索质量已达标。

现在具备明确型号、适用版本、上传版本、资料类型和业务生效日期的硬过滤。上传者通过`PUT /documents/{id}/business-metadata`提供声明依据，服务端记录actor并用版本CAS防覆盖；未知生效日期不按上传日期替代，显式生效日期过滤会排除未知记录。型号仅做去空格/大写归一，不把PTFE-5020模糊当PTFE-502。

词项Top-N在数据库内参数化计分、排序、截取；Full模式向量SQL使用同样硬条件，再做weighted RRF(k=60，词项1.0/向量1.3)和Reranker。当前词项是substring，不是BM25，未验证大型语料的查询计划或性能；业务元数据复合索引不等于全文索引。单份文档目前声明一个主要型号/适用版本，多型号混合文件需要拆分，不能假装支持全部表格行过滤。

REST检索、问答工具与MCP共用同一应用服务；这些模型调用仅处理public资料，避免云处理私密数据。原始资料和索引的项目权限仍由服务端派生。SQL/向量过滤的契约已测试，实际PostgreSQL/HNSW和Embedding质量尚未本轮验收。

## 进入小范围试用前的验收

先由业务人员对真实脱敏包独立标注问题、正常条件、证据位置和适用范围。开发集按失败案例迭代，测试集按项目/文档家族隔离；同一供应商同一规格不同颜色不能随意拆成独立样本。至少含无冲突、缺证、错版、不同型号、等价单位、表格、扫描及无答案查询。还需实际pgvector、MinerU及生产目标环境故障记录；当前定位为工程原型和开发回归。

## 长任务快照和决定的边界

新Temporal任务提交时冻结当前Evidence正文及来源hash，各阶段读取同一快照。重新索引不修改旧任务的资料含义；这不等于PLM完整的生效/作废管理。快照正文保存在业务数据库中，需按原资料保密要求运维；本轮没有添加对外读取全文快照接口。

人工决定先以command_id、actor、原因和报告版本持久化，状态为decision_pending；工作流消费后才是approved/rejected。客户端不能把“已提交决定”直接显示为“已批准”。同一决定重试不重复记人工事件，裸Signal不能跳过审批门禁。机器报告发布重试不得覆盖人工issues/usage；终态晚写不允许复活。

## 角色与文本增量

Agent角色为retrieval/material/review，业务资料类型仍为design/material/price/other。检索Agent查冻结包内证据，不自动从公网或最新项目资料补入内容；外部资料先授权入库、声明适用性，再重新提交审查。面密度规则仅对明确单型号/适用版次的g/㎡、kg/㎡做Decimal归一；复杂表格、多型号、容差与安全合格性不自动判定。

Markdown为派生阅读/导出格式，保留原件与Evidence权威；报告不会自动变成依据。上下文增强首版只加来源元信息，不能作为引文或确认业务事实。完整取舍见[本轮说明](implementation-and-interview-2026-11-03.md)。
