## 优先级与交付顺序

| 顺序 | 优化 | 完成的判断标准 |
|---|---|---|
| P0-1 | 拆分模型输出与服务端问题单Schema | 模型不生成版本、文件名、问题ID或人工状态；错误引用仍被拒绝 |
| P0-2 | 给模型发现增加比较前提校验 | 跨型号、跨适用版本、跨税口径不能被判成确定冲突；不明确则补证 |
| P0-3 | 修Temporal决定、状态同步与幂等 | 决定不被静默忽略；Activity重试不覆盖人工记录；终态可一致查询 |
| P1-1 | 建立真实字段与检索过滤 | 型号、适用版本、生效日期可以有依据地SQL过滤，不能只匹配文本 |
| P1-2 | 更严格的独立评测 | 问题级误报、遗漏、语义支持和执行失败全部可见；开发/测试隔离 |
| P1-3 | 可冻结的资料包与证据快照 | 同一次任务所有阶段使用相同解析版本，重新索引不改旧报告含义 |
| P2 | 降调用成本、补复核工作台 | 少一次无效规划调用；能直接查看两侧证据及人工处理历史 |

为面试准备，先完成P0-1/P0-2及新评测口径，再验证检索和Temporal真实恢复。开始对外试用前，P0-3不能跳过。三个领域子Agent继续封装成工具，现有边界可保留。

## 1. 模型发现与服务端字段应分开

代码依据：`src/agents/review_agents.py:39`把`findings`直接声明为`list[ReviewIssue]`；`:335`把整个Schema发给模型；`:396`直接验证；`:466`又由服务端重建引用定位。`src/domain/schemas.py:25`的引用版本是字符串。

结果是模型要输出本来不应由它决定的`evidence_refs.version`等字段。真实回归`bad-unit-converted`已经因该字段类型错误失败。把字段放宽为任意类型会掩盖边界问题。

建议新增最小`ModelFinding`：检查类型、两侧证据ID、原文支持片段、比较事实、解释及不确定性。服务端转换为`ReviewIssue`，负责ID、领域、文件/页码/版本、人工状态及最终严重级别。保留有限结构重试与明确失败；越界、无证据、伪造原文不可通过。

验收：数值型版本/伪造文件名不再进入模型契约；未知证据ID、引用未处理资料、引文不在原文中仍须失败。增加缺字段、截断和一次修复失败的定向验证，再跑同一开发集；另保留未用于调参的新包。

## 2. 从自由判断改为“事实抽取—比较前提—结论”

代码依据：`src/domain/review_rules.py:178`按型号/适用版本分组厚度，`:255`按型号/地区/税分组价格；但模型发现的`_validate_worker_review`（`review_agents.py:424`）主要验证身份、ID和处理状态，没有验证其比较前提。规则没有报错，也不妨碍模型另报一个错误冲突。

真实回归中，`ok-other-applicability`与`ok-price-tax`因此误报。继续只加Prompt不能提供同等约束。

先限定支持字段，不做通用工程推理：

| 事实 | 必须明确的前提 |
|---|---|
| 厚度 | 型号、适用版本、测量对象（涂层/总厚度）、数值、单位、原文位置；容差若有须保存 |
| 版次 | 文件编号、自身版次、生效/替代关系，不能拿供应商S7与设计D3直接比 |
| 历史价格 | 型号、地区、税、币种、面积单位、业务日期；供应商、数量等扩展字段保留未知 |

模型可提取候选事实，代码验证引文并统一单位，再按明确前提比较。输出至少区分“确定差异线索”“适用性不足待补证”“不同范围不可直接比较”“未发现该类问题”。不明确时不能猜成一致，也不能冒充确定冲突。

以事实和比较关系生成问题指纹，合并设计/材料重复发现，保留多个来源与领域贡献；不要以相似措辞直接合并不同型号问题。大包跨批次应先汇总事实再做全包比较，不能仅把批次报告拼起来。

验收：同数值等价单位、不同型号、不同适用版本、涂层与总厚度、含税/未税、同文件有效多版均有正常/异常成对案例，且检查每个问题的结论类型和两侧事实，不能只检查“是否需要复核”。

## 3. Temporal路径有实际一致性缺口

本地事务审批已经通过，不等于Temporal模式通过；`src/application/reviews.py:250`的本地分支与`:261`开始的Temporal分支是不同路径。

本次[隔离探测结果](validation-artifacts/README.md)实际验证了三个底层行为：running期间调用reject后，即使切换到等待态决定仍为空；重复保存机器报告把已resolved问题变回pending_human，审计事件由1条变0条；相同approved终态第一次更新返回True，第二次返回False。探测直接调用处理器/持久化函数，**未验证Temporal Server的调度与重试时序**。脚本为[probe.py](validation-artifacts/README.md)，仅操作独立SQLite。

### 3.1 决定可能被忽略

`src/workflows/temporal_definitions.py:177`与`:183`的Signal处理器只在状态为`awaiting_approval`时记录决定，其余状态直接返回。报告在compose Activity内已保存，但Workflow到`:264`才进入等待态；应用层`:272`发送Signal，没有传入报告锁版本或唯一决定ID。

因此存在“数据库报告已可复核—Workflow尚未进入等待态”的窗口；API可返回`decision_requested`，应用自己的处理器却忽略该决定。这里不是声称Temporal传输丢失了Signal。未处理问题会挡住approve，但不挡住有效的提前reject。

建议把决定做成持久化命令，包含command_id、review_id、expected_lock_version、actor、reason。提交与锁版本检查在事务中完成；工作流幂等处理命令并记录回执。提前命令应等待/缓存或显式拒绝，不得返回成功后忽略。需解决“决定提交后又有人改问题”的竞争；只在发Signal前多查一次状态仍有窗口。

### 3.2 报告和最终审批活动不幂等

`src/workflows/activities.py:303`保存报告后，到`:318`才结算预算并返回。`src/infrastructure/database.py:1565`对同review_id无条件覆盖issues、usage和status。如果保存成功、Activity结果未确认或随后结算失败而重试，可能覆盖已发生的人工处理和审计事件。

`activities.py:325`的最终审批调用`update_package_review_status`；后者`database.py:1638`只接受当前`awaiting_approval`。若第一次已写approved但响应丢失，重试会返回False并抛错；相同决定应当幂等成功，相反决定应明确冲突。

建议区分“写入一次机器报告”和“追加人工决定”，用review_id+generation/run标识控制首次完成；重试读取既有相同结果，不覆盖人工状态。预算结算和报告完成的中间状态须可恢复。终态更新接受相同命令重复执行，拒绝相反决定。

### 3.3 取消/失败没有同步报告状态

`temporal_definitions.py:278`和`:291`更新Workflow内状态，随后调用`settle_review_budget_activity`。该Activity（`activities.py:339`）只结算预算，没有更新报告行。故数据库可能仍显示queued或awaiting_approval，而Workflow显示cancelled/failed。

建议用显式、幂等的业务终态Activity同步报告与预算，并设计恢复对账。不能将“取消请求已提交”直接显示成“已取消”；在途Activity的写入也必须带状态/代际约束，防止取消后又写回结果。

必须补的故障验收：报告提交后让Activity失败一次；批准落库后让返回失败一次；人工等待前提交决定；两位审核人竞争；执行中及等待中取消；Worker在上述窗口重启。记录Workflow历史、DB状态、问题处理事件及预算，最终每种情况都可解释和恢复。

## 4. 结构化检索要与简历表述一致

`src/infrastructure/database.py:867`当前仅接收query、项目、租户和分级；`:890`读取全部匹配片段，随后在Python内按词项计分。没有工程型号/业务生效日期/适用版本的查询Schema和索引字段。已有RRF与pgvector代码不补足这部分。

建议从上节事实/资料元数据中建立经确认的型号、文档类型、适用版本、生效区间和状态。检索请求明确区分硬条件与语义描述，硬条件使用参数化SQL并复用于所有召回通道；模型提取的含糊条件需确认或保留歧义。上传时间不能替代业务日期，型号不能以模糊包含匹配冒充精确命中。

词项通道改为数据库中可索引的实现，中文分词与型号标识单独设计并实测；不要仅因为用了PostgreSQL就叫BM25。验证至少包含型号近似、版本相近、过期/未来生效、多相关和无答案查询。

修好Embedding权限或配置获准端点后，在相同过滤、相同语料及相同候选预算下跑词项、纯向量、RRF、RRF+Reranker。60查询/30文档全候选下的完美重排成绩仅作开发记录。扩大语料必须有有效文档与标注，不能只复制无关文本凑规模；同时记录SQL计划、候选量、延迟和内存。

## 5. 评测要能惩罚“说对一件事，又多说两件错事”

`scripts/run_business_eval.py:156`的通过条件是复核标识正确、预期问题类型和证据为实际结果子集、引用ID合法。未检验每条附加发现，也未检验问题与引文的语义关系；`:150`计算的schema_valid也没有加入correct条件。FastAPI响应Schema会做部分保护，但不等于完整领域检查通过。

保留现有24条作为开发回归，不重命名为独立测试。新协议建议：

- 对每条问题匹配检查类型、实体、属性、适用范围、左右事实和证据跨度，记录问题级TP/FP/FN；重复问题单独记录。
- 区分执行成功率、问题检测质量、字段抽取质量、引用可定位率和人工语义支持。空问题/无答案正常情形单列，分母为零不记1。
- 无法执行的应复核包不能被“完成样本Recall=100%”掩盖。另报全量成功处理比例和失败数。
- 开发与测试按真实项目/文档家族隔离，保留标注分歧；真人标签缺失时如实标成合成或开发者标注。
- 单Agent、三工具Agent、规则、规则+模型用同一批资料和相同预算对照；真实模型可重复测波动，预先固定次数，不按最好一次报告。
- 保存配置/代码/数据hash、全部attempt、错误、耗时和真实Token。`review_agents.py:530`目前按batch数填calls，批内结构修复第二次调用未在calls中体现；规划重试也应累计而非只留成功一次usage。

验收以正常包误报、关键问题漏报和失败可恢复为主，不以追到某个漂亮总分为目标。真实业务错误成本由审核人确认，不能把新设阈值写成既有客户SLA。

## 6. 资料包需要真正的证据快照

Temporal的规划、领域审查、补审、合并分别在`activities.py:111/:189/:243/:288`重新读取当前Evidence。`database.py:810`重新索引会删除并重建同文档片段，ID仍为document_id:chunk_index。报告里的SHA能追溯，但并不阻止阶段之间读到不同解析结果。

建议提交时持久化review_manifest，含文档hash、解析器/切片版本、证据ID+hash及不可变存储引用、比较范围和规则/Prompt版本。各Activity读取该manifest；原文或解析结果改变就生成新generation，不改变旧任务。无需把全部文档正文塞进Workflow历史。

验收：审查暂停时重新索引，旧任务继续使用原快照或明确失败，不能静默混用。重新提交可关联previous_review_id并展示差异，旧报告保持可解释。

## 7. 复核页面与调用成本

`frontend/src/views/ReviewDetailView.vue:30`目前证据区只展示文件、位置、版本和ID。问题的实际/预期值已有，但无法直接在问题旁查看左右原文。先复用已有资料Evidence接口做问题证据抽屉，展示原文片段、来源位置和比较前提，再做受授权的原件预览。处理记录应能看到谁、何时、为何忽略，报告原始发现与最新人工状态分别展示。

`ReviewsView.vue:34`提交没有独立submitting状态；需禁用重复提交并由服务端提供明确的请求幂等机制。长任务展示阶段、失败原因、可重试动作及取消请求/最终取消的区别。当前JSON计划可折叠为诊断详情，主视图显示检查了什么、缺什么、下一步谁处理。

`review_agents.py:128`先调用模型规划，但full模式在`:164`又强制三个领域。full直接产生确定计划即可，保留Supervisor调用子Agent工具的架构；focused需要规划时再调用模型。实测每包调用次数、Token和p50/p95后判断收益，不预报“减少30%延迟”。
